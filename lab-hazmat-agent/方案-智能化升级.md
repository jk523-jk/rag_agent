# 方案：智能化升级（详细设计）

> 前置：v2.0 已落地 Agent 化（每个 Agent 有独立 prompt 与工具白名单），工作流已下线。
> 本文按「**能测**」筛选——测不了的改进不算智能化，只算感觉。

---

## 0. 分层与优先级

```
第 3 层  答得主动   风险看板 · 异常归因 · 主动澄清        ← 从"问答"到"发现问题"
第 2 层  答得快     意图路由 · 语义缓存 · 模型分级        ← 省时省钱
第 1 层  答得准     后置校验 · 混合检索 · 重排 · 改写    ← 守住下限
```

| 顺序 | 项目 | 收益 | 成本 | 依赖 |
|---|---|---|---|---|
| P0-1 | 回答后置校验 | 消除已发生的日期/区间错答 | 0.5 天 | 无 |
| P0-2 | 混合检索（BM25 + 向量 RRF） | 条号/化学名的精确命中 | 1.5 天 | 无 |
| P1-1 | 异常归因 | 从"差 4 瓶"到"可能为什么" | 1 天 | 无 |
| P1-2 | 风险看板 | 主动发现，V2 核心卖点 | 2 天 | 四类校验已有 |
| P1-3 | 查询改写 + 别名表 | 别名/口语问法 | 1 天 | 无 |
| P2 | 重排 / 缓存 / 分级 | 质量与成本优化 | 各 0.5 天 | P0 之后才有意义 |

## 1. P0-1 回答后置校验（Verifier）✅ 已实现（2026-10-18）

> 代码：`backend/app/agent/verify.py`；接入点：`api/chat.py`（非流式直接修正，流式用 `replace` 事件覆盖）。
> 实测：同一问题连问 4 次，修复前 3/4 出现编造数值与日期，修复后 4/4 正确。

### 1.1 问题证据（实测）

| 工具返回 | 模型回答 | 性质 |
|---|---|---|
| `少量（不足 5 克）` | `10–50 克` | 区间被改写，**性质错误** |
| `数据截至 2026-10-16 20:37` | `截至 2024-04-05 16:30` | 日期被臆造 |
| 判定日期 `2026-10-17` | `当前为 2024-04-05` | 时点错误，导致结论反转 |

提示词第 10 条要求"原样照抄"，只能降低概率，不能消除。

### 1.2 设计：不信任模型输出，做机械核对

新增 `backend/app/guard/verify.py`：

```python
@dataclass
class VerifyResult:
    ok: bool
    fixed_reply: str
    issues: list[dict]      # [{kind, claim, evidence}]

def verify_reply(reply: str, tool_outputs: list[str], *, at_time: datetime) -> VerifyResult:
    """三类检查：
    A. 日期：回答里出现的 YYYY-MM-DD 必须能在 tool_outputs 或 at_time 里找到；
    B. 区间：`约 a–b 单位` / `少量（不足 n 单位）` 必须与 tool_outputs 中的原文一致；
    C. 结论词：`准予进入 / 资质过期 / 无授权 / 需双人同行` 必须是工具返回过的四值之一。
    """
```

**处理策略（按严重度分三档）**

| 情况 | 处理 |
|---|---|
| 回答里出现工具未返回的**日期** | 直接替换为工具里的"数据截至"日期；若工具无日期，追加声明"（时间以查询结果为准）" |
| **区间/数值**与工具不一致 | 替换为工具原文；同时在回答末尾附「已按查询结果校正」 |
| **结论词**不在工具返回里 | 最高危：不替换，改为**不输出结论**，返回"本次判定未取得可信结论，请重试或联系管理员"，并记 ERROR 日志 |

> 结论词这一档为什么这么严：准入结论错了会放错人，宁可答不出来。

### 1.3 接入点

`api/chat.py` 的 `/chat` 与 `/chat/stream`：
- 非流式：直接 `verify_reply` 后再返回。
- 流式：**不能边流边改**。折中方案：流式先正常输出，在 `[DONE]` 前追加一个 `{"verify": {...}}` 事件；前端在气泡下方显示"已校正 2 处"并可展开。若命中「结论词」档，则在流末尾追加一条醒目告警并作废结论样式。

需要在 graph 执行后取得工具原文 → 用 `result["messages"]` 里 `ToolMessage` 的 content 汇总，不需要改工具层。

### 1.4 验收

- 构造 10 条回归用例（日期错 4、区间错 4、结论错 2），`tests/test_offline.py` 新增 `verify` 组，要求 **10/10 检出并正确处理**。
- 线上指标：连续 50 次真实问答，人工抽查"未校正但错误"的条数为 0。

## 2. P0-2 混合检索

### 2.1 问题

纯向量检索对**精确串**弱：`第 4.2.1 条`、`CAS 67-64-1`、`GB 15603`、`氰化钾`（同义不同形）。实测问"易燃液体最多能存多少"能命中，但问"第4.2.1条写的什么"经常召不回。

### 2.2 设计

```
                   ┌── 向量检索（现有 Chroma，cosine，fetch_k=20）
query ──分词/改写──┤                                                  ──RRF融合── 重排(可选) ── top4
                   └── BM25（jieba 分词，内存索引，46 chunk 全量）
```

- 新增 `rag/bm25.py`：启动时从 `corpus/` 重新切分建内存索引（46 chunk，毫秒级），或从 Chroma 取 `documents` 建索引（更快，避免二次切分差异）。
- **RRF 融合**：`score = Σ 1/(k + rank_i)`，`k=60`。不比较两路原始分数（量纲不同，比了就是拍脑袋）。
- 元数据过滤（`kind` / `doc_name`）在**两路都生效**，避免"过滤后 RRF 再拼回不相关文档"。
- 接口保持 `retrieve_policy(query, doc_name, kind, k)` 不变，前端与工具层零改动。

### 2.3 验收

扩 `evals/cases.yaml` 到 60 条，其中 20 条是"精确串"类（条号、CAS、标准号）。指标：

| 指标 | 现状 | 目标 |
|---|---|---|
| Recall@4（全部用例） | 待测基线 | ≥ 0.90 |
| Recall@4（精确串子集） | 待测基线 | ≥ 0.85 |
| 无命中率（应召回的用例返回空） | 待测 | ≤ 5% |

> 先跑基线再改，否则无法证明变好了。

## 3. P1-1 异常归因

### 3.1 现状

`reconcile_inventory` 输出：结存 8 瓶、领用 12 瓶、差异 +4 瓶、超阈值。**只有"是什么"，没有"为什么"。**

### 3.2 设计：候选原因 + 可验证的下一步

在工具返回中追加一段「可能原因（按可能性排序）」：

| 原因 | 判定依据（用现有数据可验证） |
|---|---|
| 漏登记入库 | 领用合计 > 结存，且期间无入库流水（需新增 `hazmat_inbound` 表或在用途字段标记） |
| 重复出库 | 同一人同日同品多次领用、数量雷同 |
| 挪用未登记 | 领用记录存在但无见证人（剧毒品/易制爆） |
| 期初数据错误 | 差异恰好等于某次领用的整数倍 |
| 单位不一致 | 台账单位为瓶、领用单位为毫升（当前种子无此情况，但真实数据常见） |

**关键约束**：只说"可能是"，并给出**验证动作**（查哪张表、找谁核对），不判定责任。系统不做合规定性，这条底线沿用。

### 3.3 验收

- 用 6 组构造数据（每种原因各一组），工具输出必须把正确原因排在前二。
- 人工评审：5 位安全员看输出，认为"下一步可执行"的占比 ≥ 80%。

## 4. P1-2 风险看板（交叉发现）

### 4.1 定位

V2 需求里"人/机/料/法/环 + 交叉发现"的落地形态。现在的四类校验都要用户主动问，看板是**主动汇总**。

### 4.2 四类校验（都已有 SQL 基础）

| 类型 | 判定 | 复用 |
|---|---|---|
| 人 × 环 | 资质过期但仍有机房通行记录 | `qualifications` + `access_events` |
| 料 × 料 | 台账结存 < 期间领用 | `hazmat_inventory` + `hazmat_uses` |
| 机 × 机 | 状态"在用"但 `calibrate_due` 已过期 | `equipment` |
| 机 × 人 | 借出未还且已过 `due_time` | `equipment_loans` |

### 4.3 接口

`GET /api/risk/summary?days=30` → 统一结构：

```json
{
  "generatedAt": "2026-10-18 21:40",
  "total": 7,
  "items": [
    {"id": "r-1", "type": "person_env", "severity": "high",
     "title": "王某资质过期 12 天，10-12 仍有 LAB-3 通行记录",
     "evidence": {...}, "suggest": "核实门禁是否应拦截，并安排复审"}
  ]
}
```

严重度规则（可配置）：过期天数、是否涉及剧毒品/易制爆、是否有未见证人领用。

### 4.4 前端

- 工作台顶部替换原"演示数据"卡片区，改为「风险概览」：总数 + 四类分布 + 前 5 条。
- 新增 `/risks` 页面：按类型/严重度筛选，点击进入对应人员/设备详情。
- **明确标注"仅供参考，不构成隐患定级"**——不越界。

### 4.5 验收

- 用当前种子数据能稳定产出 3 类以上告警（已知：王某资质过期、丙酮账实不符、EQ-0002 校准过期、EQ-0007 逾期未还 → 4 类全中）。
- 接口 P95 < 300ms（4 条聚合 SQL，可并行）。

## 5. P1-3 查询改写 + 别名

### 5.1 设计

两级，先便宜后贵：

1. **别名表**（零成本，覆盖 80%）：`双氧水 → 过氧化氢`、`酒精 → 乙醇`、`烧碱 → 氢氧化钠`…维护在 `backend/app/rag/synonyms.py`，工具层匹配失败时先查别名表。
2. **LLM 改写**（只在检索前，不用于工具参数）：把口语问法扩成 2–3 个检索变体，多路检索后 RRF 合并。

### 5.2 风险

改写会引入**漂移**：把"氰化钾"扩成"钾盐"就可能召回到不相关 SDS。约束：改写只能**增加**同义词与全称，不能替换实体名；改写结果与原文一起检索，不单独使用。

## 6. 第 2 层：速度与成本

| 项 | 设计 | 预期 | 风险 |
|---|---|---|---|
| 意图路由 | 规则命中「能不能进/准入」→ 直接调 `check_lab_access`，省一次模型选工具 | 简单题省 1 次模型调用 | 规则误判会导致答非所问，需灰度 |
| 工具结果缓存 | key = `(工具名, 参数, 分钟级时间窗)`，TTL 60s，进程内 LRU | 同一轮多问省重复查询 | 数据刚变更时可能给旧值，需在回答里保留"数据截至" |
| 语义缓存 | 问题 embedding 相似度 > 0.95 且 5 分钟内 → 回放 | 高频重复问题近乎零成本 | 相似但不同的问题会串答案，阈值要保守 |
| 模型分级 | 单点查询用 `qwen-turbo`，跨域综合用 `qwen-plus` | 成本降 60% | 小模型可能不遵守工具调用格式，需评测 |

**这些都不该先做**：在"答得准"未达标前优化速度，等于把错误的答案更快地给出去。

## 7. 第 3 层：主动澄清

### 7.1 场景

| 场景 | 现在的行为 | 期望 |
|---|---|---|
| 重名（李某 ×2） | 返回两人，让用户自己看 | 先问"是硕士生李某还是本科生李某？" |
| 化学品别名 | 返回"名称不匹配 + 相近名" | 直接问"你是指过氧化氢吗？" |
| 时间不明 | 按服务器当前时间 | 保持（这个默认是合理的） |

### 7.2 实现

不需要新工具：在 `compose_prompt` 里加一条规则"当匹配到 2 个及以上候选且无法用工号/ CAS 区分时，先追问一句，不要直接判定"，并在工具返回值里显式标注 `AMBIGUOUS`，让模型有据可依。

## 8. 评测闭环（长期，必须有）

- `evals/cases.yaml` 从 18 条扩到 60+，每条含 `expect`（应命中的工具、应出现的结论词、必须出现的日期/区间）。
- `evals/run_evals.py` 输出四类指标：工具选择准确率、结论正确率、引用一致性（新增，接 P0-1）、拒答召回率。
- 每次改 prompt / 工具 / 检索，跑同一套用例，**前后对比**，把"感觉变好了"变成数字。
- 进阶：把评测接进 GitHub Actions（`workflow_dispatch` 手动触发，避免每次 push 都烧 token）。

## 10. 明确不做

- **不做微调**：语料量级不够，且微调后无法解释"为什么这么答"。
- **不做 Agent 自主规划（AutoGPT 式）**：安全场景下不可控，多步工具调用已由 LangGraph 约束。
- **不让模型生成 SQL 判断准入**：三闸必须固化 SQL，这条从 v1 起就没松过。
- **不做隐患定级**：只报事实与建议，定级交给人。
- **不引入 Neo4j 等新存储**：当前数据量与关系复杂度用不上，增加运维负担。
