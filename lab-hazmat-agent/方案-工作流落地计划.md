## 0. 定位：这份计划要落地的"工作流"是什么

**一句话**：把散在四类交叉校验里的判定，按固定顺序批量跑一遍，输出一张带证据、带责任人、带建议的风险清单。

它**不是**：

| 不是 | 原因 |
|---|---|
| 可视化节点画布（Vue Flow） | v2.0 下线的就是它；后端 0 引擎，纯前端演示。重建等于把演示品再做一遍 |
| LLM 自主规划（AutoGPT 式） | 不可复现、不可测，与本项目"判定了就有依据"的立场冲突 |
| 任意 DAG 引擎 + 用户自定义 | 本项目流程是**安全要求**（三闸顺序、校准口径），不该由用户发明 |
| 带写操作的处置流（派单/整改/通知） | MySQL 账号只有 `SELECT`；`FORBIDDEN_TOOL_NAMES` 导入时断言 |

它**是**：模板写死在代码里、步骤是纯函数、没有大模型也能跑完的**确定性巡检流水线**。

### 0.1 交付物清单

| # | 交付物 | 位置 |
|---|---|---|
| 1 | 5 个检查函数 + 单测 | `backend/app/workflows/checks/` |
| 2 | 执行器 + 运行记录存储 | `backend/app/workflows/{runner,store,models,spec}.py` |
| 3 | 4 个 HTTP 接口 | `backend/app/api/workflows.py` |
| 4 | 巡检页面 | `frontend/src/pages/InspectionsPage.vue` + 路由 + 导航 |
| 5 | 接口类型与服务层 | `frontend/src/types/index.ts`、`services/dataApi.ts` |
| 6 | ≥ 20 条离线断言 | `backend/tests/test_offline.py` |
| 7 | 本计划 + 验收记录 | 本文档 §7 |

### 0.2 明确不做（本计划范围外）

- 不做定时调度（W7 才评估，且默认走 CLI + 系统计划任务，不在进程内起 cron）
- 不做隐患定级、不做责任认定、不做自动处置
- 不提供整单导出（延续只读定位；导出等于把清单变成可外传的数据）
- 不把巡检注册成模型工具（W7 可选，见 §10 决策点 3）
- 不新增任何 Python 依赖（`asyncio` + 现有 `fetch_all` 足够）

## 1. 目标与验收

### 1.1 功能目标

| ID | 目标 | 对应需求 |
|---|---|---|
| G1 | 一次运行完成五类检查，输出统一排序的风险清单 | 需求分析-V2 G4（风险预警，当前 🔄 部分） |
| G2 | 每条 Finding 带证据、责任人、建议下一步 | §11「预警清单无人认领 → 只是报表」 |
| G3 | 历史运行可回看，同一问题跨天不重复刷屏 | 清单可用性 |
| G4 | 库不可达/单检查失败时，明确标"不完整"，绝不输出"无风险" | §8 只读与判定口径 |

### 1.2 非功能目标

| 项 | 指标 | 说明 |
|---|---|---|
| 无 LLM 依赖 | 100% | `LLM_API_KEY` 当前是占位符，巡检必须能跑 |
| 单次运行耗时 | < 3 s（本地库）／< 8 s（云库） | 5 条 SQL 并行 |
| 离线可测 | 全部 check 可用假 rows 单测 | 不依赖 MySQL |
| 只读 | 0 条写语句 | 全部经 `fetch_all` |
| 依赖 | 0 新增 | — |

### 1.3 验收基线（最关键的一条）

用现有 `03_seed.sql` + `06_equipment_seed.sql` 种子数据，`ins-daily-risk` 跑完必须**恰好**产出以下 5 条 finding：

| # | check | 主体 | 期望 severity | 依据 |
|---|---|---|---|---|
| 1 | `person_env` | 王某（person 1）/ LAB-3 | high | 安全考试合格证过期 10 天，但 3 天前仍有「进·通过」记录 |
| 2 | `material` | 丙酮（item 1）/ LAB-3 3号柜 | high | 结存 8 瓶，近 30 天领用 12 瓶，超阈值 |
| 3 | `machine_machine` | EQ-0002 / LAB-2 | high | 校准过期 20 天，状态仍为「在用」 |
| 4 | `machine_person` | EQ-0007 / 赵某（person 5） | medium | 未归还，逾期 3 天 |
| 5 | `double_entry` | 张某（person 4）/ LAB-5 | high | `needs_double=1` 的剧毒品间，`companion_no=0` 单人进入 |

**同时必须不出现**：

- EQ-0008（状态「报废」）→ 不该进校准清单
- EQ-0004 / EQ-0006（储存设施，`calibrate_due IS NULL`）→ 不该进校准清单
- EQ-0007 的校准（15 天后到期）→ 日巡 `warn_days=0` 时不报；这是 `machine_machine` 与 `machine_person` 报的是同一台设备但不同问题，两条都在预期内
- 李某（person 2）授权已撤销 → 若窗口内无通行记录，`person_env` 不报（它不是"违规发生"，只是"授权状态异常"）

> 少一条 = 判定口径与工具层不一致；多一条 = 误报。两种情况都视为不通过。

## 2. 系统设计

### 2.1 分层

```
api/workflows.py        参数校验 / audience 脱敏 / HTTP 状态码
      ↓
workflows/runner.py     统一 as_of 快照、并发、单检查隔离、耗时、落盘
      ↓
workflows/checks/*.py   纯函数 async run(ctx) -> list[Finding]   ← 只依赖 fetch_all
      ↓
db/connection.fetch_all 唯一只读入口 + AST 护栏 + LIMIT 注入 + 语句超时
```

**为什么是这个形状**（与三条既有约束一一对应）：

1. `fetch_all` 是现成的唯一取数入口，check 不自己开连接，只读护栏免费继承（`sql_guard` 顶层只接受 `Select/Union`，子查询、`GREATEST`、`DATEDIFF` 都放行）。
2. check 返回**结构化 Finding**，不返回给模型看的字符串——现有 `@tool` 返回 `str` 是为人/模型阅读，巡检要的是可排序、可去重、可跳转的数据。
3. runner 不涉及任何 LLM，因此 `LLM_API_KEY` 为空也能跑。

### 2.2 与现有工具的关系：复用判定，不复用排版

| 现有资产 | 巡检怎么用 |
|---|---|
| `access_tools._judge` | `person_env` 的阈值与闸序**必须**与它一致；不直接调用（它按人查），但口径对齐并由 §6.2 的一致性断言守住 |
| `access_tools` 双人闸逻辑 | `double_entry` 必须复刻"按天取最大同行人数"的聚合方式，否则误报 |
| `inventory_tools.to_interval` / `masked_quantity` | 脱敏唯一出口，`audience=agent` 时必须走它 |
| `equipment_tools._calibrate_text` | 文案复用；判定仍以 `calibrate_due` 而非 `status` |
| `get_settings().loss_threshold_abs / ratio` | `material` 的阈值参数，直接读配置，不写死 |
| `access_tools._SQL_*` | **不复用**。工具是"按人/按设备查"，巡检是"全库扫描"，查询形态本就不同；但**判定条件**必须一致 |

### 2.3 数据模型

```python
# workflows/models.py
from dataclasses import dataclass, field
from datetime import datetime
from typing import Any, Literal, Protocol

Severity = Literal["high", "medium", "low"]
CheckStatus = Literal["ok", "error", "skipped"]
RunStatus = Literal["success", "partial", "failed"]


@dataclass(frozen=True)
class CheckContext:
    """一次运行内所有 check 共享的上下文。as_of 是唯一时间源。"""
    as_of: datetime            # 快照时刻，所有 SQL 用它而不是 CURDATE()
    window_from: datetime      # 观察窗口起
    window_to: datetime        # 观察窗口止（= as_of）
    params: dict[str, Any]     # 模板参数（lab_id / window_days / calibrate_warn_days …）


@dataclass
class Finding:
    key: str                   # 去重键，跨天稳定：f"{check}:{subject_id}"
    check: str
    severity: Severity
    title: str                 # 一句话结论，模板拼接，不由模型生成
    subject_type: Literal["person", "equipment", "item", "lab"]
    subject_id: str            # 用于跳转：person_id / equip_id / item_id / lab_id
    subject_label: str         # 展示用："王某（T2023001）"
    evidence: list[dict]       # [{"label": "合格证有效期至", "value": "2026-10-09"}]
    owner: str                 # 从 labs.mgr_name / equipment_loans.approver 取
    owner_hint: str = ""       # "实验室负责人" / "批准人"
    suggest: str = ""          # 建议下一步，禁止写成处置指令
    links: list[dict] = field(default_factory=list)   # [{"label": "人员详情", "to": "/persons/1"}]
    first_seen: str = ""       # 首次发现日期，跨 run 继承
    days_open: int = 0         # 持续天数


@dataclass
class CheckResult:
    id: str
    label: str
    status: CheckStatus
    duration_ms: int
    count: int
    error: str = ""


@dataclass
class RunReport:
    run_id: str
    workflow_id: str
    workflow_name: str
    started_at: str
    finished_at: str
    duration_ms: int
    status: RunStatus
    as_of: str
    params: dict
    counts: dict[str, int]          # {"high": n, "medium": n, "low": n, "total": n}
    checks: list[CheckResult]
    findings: list[Finding]
    incomplete_reason: str = ""     # status=partial 时说明缺了哪几项


class Check(Protocol):
    id: str
    label: str
    async def run(self, ctx: CheckContext) -> list[Finding]: ...
```

### 2.5 执行器语义（runner.py）

| 语义 | 实现 | 理由 |
|---|---|---|
| **统一时间** | `as_of = datetime.now().replace(microsecond=0)`，作为 SQL 参数 `%(as_of)s` 传入 | 现有工具用 `CURDATE()`，离线测试无法固定时间；巡检必须可复现 |
| **单检查隔离** | 每个 check 包 `try/except Exception`，失败记 `status=error` | 一条 SQL 挂了不该让整单白跑 |
| **整体结论** | 任一 check `error` → `RunReport.status="partial"`，写 `incomplete_reason` | 绝不能把"没查到"渲染成"没问题" |
| **并发** | `asyncio.gather`，信号量 = `workflow_concurrency`（默认 5） | 连接池 `pool_max=10`，5 个并行安全 |
| **总超时** | `asyncio.wait_for(..., workflow_timeout_seconds)` | 云库慢时给个上限 |
| **并发互斥** | 每个 workflow_id 一把 `asyncio.Lock`，已在跑则 409 | 避免用户连点两次把池打满 |
| **排序** | `(-severity_rank, -days_open, check_order)` | 高危且积压久的排前面 |
| **去重/继承** | 读最近一次 `success` 报告，同 `key` 继承 `first_seen`，算 `days_open` | 清单不膨胀，且能看出"这问题挂了多少天" |

`run_id` 格式：`run-20261019-143000-a1b2`（时间 + 4 位 hex）。

### 2.6 存储（复制 `agents/store.py` 的成熟模式）

```
data/
├── agents.json                  # 已有
└── runs/
    ├── index.json               # 最近 50 次摘要（列表页只读这个）
    └── run-20261019-143000-a1b2.json   # 完整报告
```

- 原子写：先写 `.tmp` 再 `os.replace`，复用 `agents/store.py::_write` 的写法
- 索引项：`{run_id, workflow_id, workflow_name, started_at, status, counts, duration_ms}`
- 保留策略：`workflow_run_retention`（默认 50），超出的按时间删文件 + 删索引项
- **写的是平台运行记录，不是实验数据**——与 `agents.json` 同一边界，不违反只读原则
- 已知代价（照抄 `store.py` 的坦诚）：不支持多副本并发写；多副本部署需换存储

### 2.7 脱敏口径（必须在这里定死）

| audience | 谁用 | 剧毒品/易制爆数量 | 实现 |
|---|---|---|---|
| `admin`（默认） | 前端控制台，登录者本就是实验室管理者 | 精确值 | 与 `api/data.py` 口径一致 |
| `agent` | 将来若把巡检结果喂给模型 | `masked_quantity` 区间 | 出口统一转换 |

规则：

1. `Finding.evidence` **内部存原始值**，落盘也是原始值（磁盘在服务端，与 `data.py` 同级）。
2. `GET /runs/{id}`、`POST /run` 响应体**按 `audience` 转换后输出**。
3. `audience=agent` 时，序列化后不得出现敏感化学品的精确数字——由 §6.3 的断言守住。
4. **不提供整单导出接口**（§0.2）。

### 2.8 API 契约

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/workflows` | 模板列表（含 `params` schema、`checks` 组成） |
| POST | `/api/workflows/{id}/run` | body `{params?, audience?}`，同步执行并返回完整 `RunReport` |
| GET | `/api/workflows/runs?limit=20&workflow_id=` | 历史摘要列表（读 `index.json`） |
| GET | `/api/workflows/runs/{run_id}?audience=admin` | 单次完整报告 |

状态码：

- `404` 模板或 run 不存在
- `409` 同一模板正在运行
- `503` 数据库未就绪（复用 `data.py` 的 `pool_ready()` 判断）
- `500` 内置 SQL 被护栏拦截（理论不发生，**必须记 error 日志**，与 `data.py` 一致）

```
└─ Finding 详情 AppDrawer：证据键值对 + 建议 + 责任 + 跳转链接
```

**关键 UI 规格（三条硬要求）**

1. **`partial` 与「0 项异常」不可混淆**：前者红色 banner + 明确"不完整"；后者绿色 + "未发现异常"。这是本项目一贯的立场（区分"查不到"与"没问题"）。
2. **空态**：从未运行 → `EmptyState`「尚未运行巡检」+ 主按钮；不是空白表格。
3. **数据来源徽标**：沿用 `workspace.dataSource` 的写法，显示「实时数据库 · 读取于 14:30:00」。

> **不要**给 `InspectionRun` 加 `isMock` 字段。`LogEntry.isMock` 是字面量 `true`，真实数据塞不进去——这正是若要把巡检接进 `/logs` 时必须先改类型的地方（见 §10 决策点 3）。

## 3. 检查项设计（5 个）

> 通用约定：所有 SQL 通过 `fetch_all` 执行；时间一律用 `%(as_of)s` / `%(t0)s` / `%(t1)s` 传参，**不写 `CURDATE()`**；`LIMIT` 由护栏注入或显式写。

### 3.1 `person_env` — 人 × 环：资质过期仍通行

```sql
SELECT p.id AS person_id, p.name, p.emp_no,
       l.lab_id, l.lab_name, l.needs_double, l.mgr_name,
       MAX(q.expire_date)                         AS cert_expire,
       DATEDIFF(%(as_of)s, MAX(q.expire_date))     AS expired_days,
       COUNT(*)                                   AS entry_count,
       MAX(a.event_time)                          AS last_entry_at
FROM access_events a
JOIN persons p  ON p.id = a.person_id
JOIN labs    l  ON l.lab_id = a.lab_id
JOIN qualifications q
       ON q.person_id = p.id AND q.cert_type = '安全考试合格证'
WHERE a.direction   = '进'
  AND a.auth_result = '通过'
  AND a.event_time >= %(t0)s
  AND a.event_time <= %(t1)s
GROUP BY p.id, p.name, p.emp_no, l.lab_id, l.lab_name, l.needs_double, l.mgr_name
HAVING MAX(q.expire_date) < %(as_of)s
ORDER BY expired_days DESC
```

**三个必须踩准的点**

1. `MAX(q.expire_date)` 对应 `_judge` 的"每人只取最新一条合格证"。用 `MAX` 而不是逐行，避免换证/复审产生重复 Finding。
2. `JOIN` 而非 `LEFT JOIN` 资格表：无合格证记录的人不在这里报（那是"缺资质"而非"资质过期"，属另一类）。若也要报"无证"，改 `LEFT JOIN` 并在 `HAVING` 加 `OR MAX(q.expire_date) IS NULL`，**作为可选开关**，默认关闭以免首版噪声过大。
3. `needs_double` 参与定级：要求双人的实验室，同一问题**升一级**。

**severity**

| 条件 | 级别 |
|---|---|
| `expired_days > 30` | high |
| `7 < expired_days <= 30` | medium |
| `1 <= expired_days <= 7` | low |
| 上述基础上 `needs_double = 1` | 升一级 |
| 上述基础上 `entry_count >= 3`（重复违规） | 再升一级（封顶 high） |

**owner**：`labs.mgr_name`；**links**：`/persons/{id}`。

### 3.2 `material` — 料 × 料：台账与领用不符

```sql
SELECT i.item_id, i.chem_name, i.cas_no, i.hazard_class, i.lab_id, i.cabinet_no,
       i.quantity      AS book_qty, i.unit,
       COALESCE(SUM(u.quantity), 0)                          AS used_qty,
       COUNT(u.id)                                          AS use_count,
       SUM(CASE WHEN u.witness_id IS NULL THEN 1 ELSE 0 END) AS no_witness_count
FROM hazmat_inventory i
LEFT JOIN hazmat_uses u
       ON u.item_id = i.item_id
      AND u.use_time >= %(t0)s AND u.use_time <= %(t1)s
GROUP BY i.item_id, i.chem_name, i.cas_no, i.hazard_class, i.lab_id, i.cabinet_no, i.quantity, i.unit
HAVING (COALESCE(SUM(u.quantity), 0) - i.quantity)
       > GREATEST(%(loss_abs)s, i.quantity * %(loss_ratio)s)
ORDER BY (COALESCE(SUM(u.quantity), 0) - i.quantity) DESC
```

**要点**

1. 阈值直接读 `get_settings().loss_threshold_abs / loss_threshold_ratio`，与 `reconcile_inventory` 完全同源。`GREATEST` 对应工具里的 `max(...)`。
2. 无期初结存，按"周转校验"（领用超过结存）——与工具 `opening_qty=None` 分支一致。**不要**在巡检里假装知道期初。
3. `no_witness_count > 0` 且危险类别属剧毒品/易制爆 → 追加一条独立 Finding（双人领用缺见证人），不要塞进同一条 evidence 混着说。

**severity**：`hazard_class ∈ {剧毒品, 易制爆}` → high（无论差额多少）；其余：差额 > 2×阈值 → medium，否则 low。

**脱敏**：`evidence` 里的 `book_qty` / `used_qty` / 差额，在 `audience=agent` 时全部走 `to_interval`，差额写 `"已按区间处理，不提供精确差值"`（照抄 `reconcile_inventory` 的措辞）。

### 3.3 `machine_machine` — 机 × 机：在用但校准过期

```sql
SELECT e.equip_id, e.equip_name, e.category, e.lab_id, e.status,
       e.calibrate_due, p.name AS keeper_name, k.mgr_name,
       DATEDIFF(e.calibrate_due, %(as_of)s) AS days_left   -- 负数=已过期
FROM equipment e
LEFT JOIN persons p ON p.id = e.keeper_id
LEFT JOIN labs    k ON k.lab_id = e.lab_id
WHERE e.calibrate_due IS NOT NULL
  AND e.status <> '报废'
  AND DATEDIFF(e.calibrate_due, %(as_of)s) <= %(warn_days)s
ORDER BY e.calibrate_due
```

**要点**

1. **只看 `calibrate_due`，不看 `status`**——台账里存在"状态在用、校准早过期"的记录（EQ-0002 就是），看 `status` 会漏判。这是项目反复强调的一条。
2. `calibrate_due IS NULL` 的储存设施（EQ-0004/EQ-0006）天然被排除。
3. `status='报废'` 排除（不再送检）；`status='维修中'` **保留**（EQ-0005 校准 30 天后到期、维修中，属"将到期"预警，不是过期）。
4. `warn_days` 参数：日巡传 0（只看已过期），设备周检传 30（含将到期）。**这是同一个 check 的两种用法**，不是两个 check。

**severity**：`days_left < -60` → high；`-60 ≤ days_left < 0` → medium；`0 ≤ days_left ≤ warn_days` → low。类别为「分析仪器 / 检测仪器」时升一级（按规定不得用于出具数据）。

**owner**：`keeper_name`，`owner_hint="保管人"`；缺失时回落 `mgr_name`。

### 3.4 `machine_person` — 机 × 人：设备借出逾期

```sql
SELECT l.id AS loan_id, l.equip_id, e.equip_name, e.lab_id, e.status AS equip_status,
       l.person_id, p.name, p.emp_no,
       l.borrow_time, l.due_time, l.approver, l.purpose,
       DATEDIFF(%(as_of)s, DATE(l.due_time)) AS overdue_days
FROM equipment_loans l
JOIN equipment e ON e.equip_id = l.equip_id
LEFT JOIN persons p ON p.id = l.person_id
WHERE l.return_time IS NULL
  AND l.due_time < %(as_of)s
ORDER BY overdue_days DESC
```

**要点**：以 `return_time IS NULL` 判未还，**不看 `status` 字段**（与 `check_equipment_loan` 一致，status 可能未同步）。`equip_status='维修中'` 且未归还 → 在 evidence 里加一条附注「设备已转维修，需核实状态是否未同步」，与工具文案对齐。

**severity**：`overdue_days > 7` → high；`1–7` → medium。
**owner**：`approver`，缺失回落 `labs.mgr_name`；**links**：`/equipment/{equip_id}`、`/persons/{id}`。

### 3.5 `double_entry` — 双人闸：要求双人的实验室单人进入

**必须按天聚合**，否则会误报"同一天既单人又双人进入"：

```sql
SELECT d.person_id, p.name, p.emp_no, d.lab_id, l.lab_name, l.hazmat_class, l.mgr_name,
       COUNT(*)   AS solo_days,
       MIN(d.day) AS first_day,
       MAX(d.day) AS last_day
FROM (
    SELECT person_id, lab_id, DATE(event_time) AS day, MAX(companion_no) AS max_companion
    FROM access_events
    WHERE direction = '进' AND auth_result = '通过'
      AND event_time >= %(t0)s AND event_time <= %(t1)s
    GROUP BY person_id, lab_id, DATE(event_time)
) d
JOIN labs    l ON l.lab_id = d.lab_id AND l.needs_double = 1
JOIN persons p ON p.id = d.person_id
WHERE d.max_companion < 1
GROUP BY d.person_id, p.name, p.emp_no, d.lab_id, l.lab_name, l.hazmat_class, l.mgr_name
ORDER BY solo_days DESC
```

**要点**：内层 `MAX(companion_no)` + 外层 `< 1` 精确对应 `access_tools` 的"任一次满足即为满足"；`companion_no IS NULL` 与 `0` 都算单人（`MAX` 忽略 NULL，故在 evidence 里注明"未记录同行人数"）。

**severity**：`hazmat_class` 含「剧毒品」→ high；其他 `needs_double=1` → medium；`solo_days >= 3` 升一级。

> 种子数据里张某（person 4）1 天前单人进 LAB-5，**基线应报出这条**（§1.3 第 5 条）。

## 附：为什么不是"写个 YAML 让用户配流程"

一句话：**本项目的流程没有可配置的空间**。

三闸的顺序（资质 → 授权 → 双人）、校准看哪个字段、脱敏按哪个类别——这些都是安全要求，`需求文档 §8` 已明确"判定用固化 SQL，不用模型生成"。一个可配置的编排器，能让用户把三闸顺序调换、把校准判定换成看 `status`，那它就在允许用户配置出一个**错误的安全判定**。

真正需要"配置"的只有三样：观察窗口、时间范围、严重度阈值——这三样是参数，不是流程。所以模板写成代码，参数走表单。

这也是这一版与 v2.0 那个画布最本质的区别：**那一版编排的是节点，这一版编排的是判定。**
